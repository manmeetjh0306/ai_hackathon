BUILD PROMPT — AQUAWATCH WATER OPERATIONS DASHBOARD
==================================================

You are a senior React engineer, data engineer, product designer, and water-utility operations specialist. Build the complete project described below inside the current sandbox workspace. Work autonomously, inspect the supplied files first, make reasonable implementation decisions, and do not stop at a wireframe. Deliver a polished, runnable, production-buildable application.


PRIMARY OBJECTIVE
-----------------

Create “AquaWatch,” a frontend-first React JavaScript control-room dashboard for intelligent water-network monitoring and incident response.

The application must:

1. Analyze the supplied Excel data correctly.
2. Detect and explain pressure-related anomalies from the supplied enriched data.
3. Present all important operational and management KPIs clearly.
4. Demonstrate an end-to-end agentic workflow from alert detection to field response.
5. Visually distinguish observed historical data from simulated live events.
6. Match the UI/UX specification in this prompt exactly and consistently.
7. Be responsive, accessible, secure, tested, and successfully compile for production.

Do not build a generic admin template. The result must look like a professional water-utility operations center.


SOURCE FILES
------------

The workspace should contain these data and requirements files:

- AssetIQ_Data_10thAug_v2.xlsx — authoritative enriched dashboard dataset
- AssetIQ_Data_10thAug.xlsx — smaller reference dataset

- README.md — anomaly and workflow business rules
- Prompts.docx — source description

Use AssetIQ_Data_10thAug_v2.xlsx as the authoritative source for dashboard analytics. Never modify any source workbook.

Expected authoritative data facts:

- 23,200 sensor readings
- 100 assets
- 63 DMAs represented in readings
- Coverage from 1 January through 20 August 2026
- 3,480 anomalies/incidents
- 15.0% anomaly rate
- Severity: 696 Critical, 1,044 High, 870 Medium, 870 Low
- Categories: 988 Leakage, 876 Burst Risk, 645 Pump Performance, 541 Meter Irregularity, 430 Low Pressure
- 171,334 represented customer-impact events across incidents
- 24,776 predicted complaints
- 95.1% notification delivery rate
- 29.5% workflow SLA breach rate, or 70.5% compliance
- 19.3-hour average work-order turnaround
- Average incident risk score: approximately 66.08
- All supplied historical incidents are resolved and work orders are closed

Validate these numbers programmatically. If the workbook differs, calculate from the actual workbook and document the variance instead of hardcoding false values.

-------------

Create scripts/build-data.mjs.

The script must:

1. Read AssetIQ_Data_10thAug_v2.xlsx with ExcelJS.
2. Read and normalize these sheets:
   - DIM_AOCD_DMA

   - DIM_FieldEngineer

   - FACT_WorkOrders
   - FACT_OutageTimeline
3. Convert Excel timestamps into valid ISO dates.
4. Convert numeric fields into JavaScript numbers.
5. Convert missing Data_Status values to “Unspecified.”
6. Retain the IDs required for joins and incident drill-downs.
7. Calculate the verified summary KPIs.
8. Write public/data/dashboard.json.
9. Print generated row counts to the terminal.
10. Fail clearly if a required sheet is missing.

Never describe blank Data_Status records as “Projected.” Do not infer provenance that is not present in the data.

Historical customer impact is aggregated per incident. Label it “represented customer-impact events” or “customers impacted across incidents”; do not call it unique customers.

Predicted complaints are model output. Never claim the dataset proves actual complaints or complaint reduction.


LIVE SIMULATION
---------------

The historical workbook contains only resolved incidents. Therefore:

- Derive seven deterministic demonstration alerts from the latest High and Critical historical incidents.
- Give them IDs such as LIVE-001.
- Set recent simulated detection times relative to the current browser time.
- Include New, Investigating, Acknowledged, and Crew assigned states.
- Mark every simulated object and screen section as “Simulated live.”
- Mark historical data as “Observed history.”
- Never silently mix simulated KPIs into observed historical KPIs.
- Store operator actions in localStorage.
- Provide a reset-simulation icon in the filter bar.
- No action may contact a real customer, engineer, or external service.

Supported simulated actions:

- Acknowledge alert
- Start investigation
- Notify affected customers
- Assign recommended engineer
- Persist state locally
- Reset to the deterministic seed state
